## SQL/database findings

Core DDL has `users`, `products`, `reviews`, `review_variants`, and `fraud_predictions`; primary/foreign keys and unique node index exist, plus a rating range check. Index DDL adds user/product/date, composite user-product, label/split, variant and run ID, and descending fraud score indexes. There are no explicit constraints for binary labels, prediction score range, non-null review identity references, or update/delete behavior. Some indexes may duplicate PK/unique index coverage and should be query-plan justified.

The table decomposition is broadly 3NF for identity entities and per-review attributes, but it is not sufficient to declare the entire application schema 3NF: the separate Prisma schema models an additional application/research-run system with overlapping review/user/product entities and no defined mapping. `advanced_sql.sql` defines a view/procedure/trigger, but these are not part of core `data_pipeline/sql` DDL. `viz/sql/explain_demos.sql` and `sql_equivalents.sql` exist; dashboard comparison values are also hardcoded, so distinguish runnable SQL from measured output.

Neo4j has uniqueness constraints on `User.user_id`, `Product.prod_id`, `Review.review_id`; sync creates `WROTE`, `ABOUT`, and optional `CAMO_LINK` relations in batches. No migration/version marker, deletion reconciliation, vector propagation, or transactional cross-database consistency exists. Neo4j is treated as a projection and needs a repeatable outbox/reconciliation contract if it is operational data.
